1

Architettura generale

Un solo database, molti clienti

Database unico (es. alphatrace_ace). Il cliente si identifica con slug (demo, alphatrace_boa, …). Non si crea un DB per tenant come in Stancl/MySQL.

🔒
Cos'è RLS (Row Level Security)? PostgreSQL filtra automaticamente le righe in base al tenant attivo nella sessione. Senza SET app.current_tenant_id = '1', le query su tabelle tenant-scoped restituiscono zero righe.

Schema (moduli logici) — versione semplificata

core
Identità SaaS e sicurezza: tenant, utenti, ruoli, permessi, organizations e domini. Base per RLS e risoluzione multi-tenant.
Core
master_data
Dati anagrafici unificati: categorie e tipi prodotto, siti e regole di stoccaggio minime. Unisce catalog + location per semplicità.
Core

Transazioni operative: unità tracciate, storico eventi, ordini di lavoro (ODL), righe ODL, spedizioni e assegnazioni.
Core

Storico informativo obbligatorio: chi ha fatto cosa e quando su UI/API. Da mantenere semplice senza feature avanzate.
Core
🧩
Scelta architetturale attuale: pochi blocchi, manutenzione facile Per la fase iniziale il modello consigliato è: core + master_data + operations + audit.

Contesto tenant in ogni sessione

Prima di interrogare o scrivere dati di business:

SQL 
-- Obbligatorio all'inizio di ogni sessione / query
SET app.current_tenant_id = '1';

-- In Laravel il middleware InitializeTenancy esegue l'equivalente:
-- set_config('app.current_tenant_id', $tenant->id, false)
🚫
Senza questo SET, RLS restituisce zero righe Ogni nuova scheda SQL in DBeaver è una sessione nuova — ricordare di aggiungere sempre il SET prima di qualsiasi query su tabelle tenant-scoped.

Tabelle principali

Riferimento rapido — non serve memorizzare tutto; usare durante sviluppo o query SQL.

core (12 tabelle)

Ruolo infrastrutturale: layer di identità e accesso del SaaS. Ogni riga di business è legata a un tenant_id; le policy RLS su questo schema (e sugli altri) filtrano in base a app.current_tenant_id impostato a inizio sessione o request API.
  • tenants — record del cliente (es. slug = demo); non si crea un database PostgreSQL per tenant.
  • tenant_domains — risoluzione hostname → tenant (produzione); in dev spesso si usa header X-Tenant.
  • users / roles / permissions — autenticazione applicativa e RBAC; token Sanctum in core.personal_access_tokens.
  • organizations — anagrafiche operative (cliente, fornitore, vettore); referenziate dagli ODL in operations.
Non contiene: beni fisici serializzati, magazzini dettagliati né ordini di lavoro.

master_data (4 tabelle)

Ruolo infrastrutturale: dati anagrafici unificati per ridurre il numero di schemi. Include sia catalogo prodotto sia ubicazioni minime.
  • product_categories — famiglia (es. valigie); flag is_traceable, is_perishable guidano validazioni a valle.
  • product_types — modello/SKU concreto; ogni tracked_units punta a un product_type_id.
  • sites — magazzino/hub/sede solo se utile operativamente; nessun obbligo di modellazione avanzata in MVP.
  • site_storage_slots — opzionale: abilitare solo se serve controllo forte su cosa può essere stoccato dove.
Distinzione importante: qui non esiste numero di serie né QR — quelli vivono in operations (asset operativi).

product_typesModello concreto (codice, nome, validità, metadata)
sitesLuogo fisico essenziale (code, name, organization_id opzionale)
site_storage_slotsRegola opzionale site ↔ tipo prodotto

operations (8 tabelle)

Ruolo infrastrutturale: cuore operativo con tutto il transazionale giornaliero: unità tracciate, eventi e ordini di lavoro.
  • identifier_batches / identifiers — generazione e registro codici QR/barcode.
  • tracked_units — pezzo fisico univoco per tenant (serial_number) con stato attuale.
  • tracked_unit_events — journal append-only: ogni cambio stato/ubicazione rilevante.
  • work_orders / work_order_lines — processo ODL e collegamento unità ↔ ODL.
Regola operativa: stato corrente su tracked_units; cronologia su tracked_unit_events; ordini su work_orders.

identifier_batchesLotto di codici QR/barcode generati

tracked_unit_eventsStorico append-only dell'unità (vedi sezione 5)

Campi chiave di tracked_units: serial_number (unico per tenant), lifecycle_status_code, product_type_id, identifier_id, site_storage_slot_id (nullable), metadata (JSON).

audit (1 tabella)

Ruolo infrastrutturale: audit trail applicativo (chi ha fatto cosa nell'interfaccia o API). Da mantenere obbligatorio ma semplice: valore informativo e storico operativo.
  • Tabella tipica: audit_events — modulo, azione, payload JSON, riferimento utente.
  • Evitare subito strutture avanzate: basta scrivere evento, utente, timestamp, modulo e azione.
Non confondere con: operations.tracked_unit_events (eventi di dominio sull'unità tracciata). I due flussi convivono e servono scopi diversi.
TabellaDescrizione
audit_eventsAzioni utente nell'app (modulo, azione, payload). Storico informativo; non sostituisce lo storico di dominio in tracked_unit_events.
3A

Flusso pneumatici (TirEco / PFU)

Tracciamento completo del pneumatico: produzione, installazione, presa in carico, rivendita usato oppure smaltimento tramite consorzio.

1
Censire categoria e tipo pneumaticomaster_data.product_categories + master_data.product_types
2
Generare identificativo univocooperations.identifier_batches + operations.identifiers (microchip/QR)
3
Creare anagrafe unita' pneumaticooperations.tracked_units con seriale, DOT, owner iniziale e stato
4
Installazione su veicolo e cambio ownerAggiornare owner/km/data e registrare evento in operations.tracked_unit_events
5
Presa in carico da gommista/officinaVerifica titolarita', apertura operations.work_orders e righe in work_order_lines
6
Esito operativoRivendita usato (nuovo owner) oppure consegna a consorzio e stato finale di smaltimento
7
Audit obbligatorioOgni passaggio critico registra traccia in audit.audit_events
3B

Flusso caldaia (esempio manutenzione)

Esempio dominio tecnico: dalla registrazione impianto alla manutenzione periodica, fino a sostituzione/dismissione.

1
Definire tipo caldaiamaster_data.product_categories + master_data.product_types
2
Definire luogo impiantomaster_data.sites e, se serve, site_storage_slots
3
Creare unita' caldaiaoperations.identifiers + operations.tracked_units (seriale e stato installato)
4
Aprire ordine interventooperations.work_orders + work_order_lines + assegnazione tecnico
5
Registrare esito manutenzioneAggiornare stato e scrivere dettagli in operations.tracked_unit_events
6
Chiusura ciclo tecnicoNuovo work order per sostituzione/dismissione e audit finale in audit.audit_events
✅
Regola valida in tutti i flussi Stato corrente in operations.tracked_units · Storico dominio in operations.tracked_unit_events · Storico utente in audit.audit_events
4

Nuovo cliente (tenant)

Creare un nuovo cliente

Solo righe nel DB esistente — niente nuovo database né migration “per tenant”.

1
Insert in core.tenantsOnboarding diretto su DB operativo
2
Insert in core.tenant_domainsMapping hostname → tenant
3
Seed ruoli, utente admin e permessiSolo dati necessari al bootstrap MVP
4
L'applicazione risolve il tenantPer dominio, query ?tenant= o header X-Tenant

Configurazione Laravel (.env)

.env 
DB_CONNECTION=pgsql
DB_DATABASE=alphatrace_ace
TRACE_CORE=true
TRACE_DEFAULT_TENANT_SLUG=demo

Test di connessione

Bash 
curl -H "X-Tenant: demo" http://127.0.0.1:8000/api/trace/health

Query storico

SQL 
SET app.current_tenant_id = '1';

SELECT event_type, from_value, to_value, occurred_at
FROM operations.tracked_unit_events
WHERE tracked_unit_id = 1
ORDER BY occurred_at DESC;

Esempio inserimento cambio stato

SQL 
INSERT INTO operations.tracked_unit_events (
    tenant_id, tracked_unit_id, event_type,
    from_value, to_value, actor_user_id
) VALUES (
    1, 1, 'status_change',
    'initial', 'in_stock', 1
);

Installare la tabella (se manca)

Opzione A — Laravel: php artisan migrate (migration create_tracked_unit_events_table).

Opzione B — SQL: eseguire database/sql/trace_core/001_tracked_unit_events.sql con psql.

⚠️
Una sola opzione Migration Laravel oppure SQL manuale — mai entrambe sullo stesso DB.

Checklist

Prima di dire che un ambiente Trace Core è operativo:

  • ☐ PostgreSQL creato e script trace_core applicati
  • ☐ Almeno un tenant con utente admin, ruoli e permessi seedati
  • ☐ Ogni sessione SQL/API imposta app.current_tenant_id
  • ☐ Tabella tracked_unit_events presente
  • ☐ Ogni cambio di stato importante genera un evento
